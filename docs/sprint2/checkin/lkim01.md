1. What did you implement so far in the sprint, and what remains?

I wrote the issue for Part 2 of the slideshow feature (#80), covering image uploads and transition-speed controls, and reviewed a teammate's issue for stale-document indicators in the sidebar. I have also implemented most of Part 2. Users can pick images from their computer, which upload through Outline's existing attachment storage. Each image shows its own progress bar, and failed uploads show an error with Retry and Remove buttons. Images appear in the order they were selected, even if they finish uploading in a different order. A toolbar dropdown lets users pick a transition speed (2s to 10s). The speed is saved with the slideshow, and Part 1 slideshows keep the 3-second default. I added automated tests for uploads, speed changes and persistence, and the existing editor tests still pass. What remains is testing by hand in the browser, then opening a pull request and getting it reviewed and merged.

2. What is one thing you learned about the codebase or about software engineering practice?

I learned how much faster a feature goes when it builds on existing infrastructure instead of reinventing it. The slideshow uses the same upload function as regular image blocks, so it got attachment storage, permissions and the document's upload notices without new server code. The speed control plugs into the same selection toolbar that images and code blocks use. I also learned how to show temporary state in the ProseMirror editor. Upload progress shouldn't be saved in the document, so I attached it as a decoration on the slideshow node. The decoration follows the node as the document changes and is passed to the component for rendering. Finally, writing detailed acceptance criteria before coding paid off: I could turn most of them directly into test cases, which made it clear when the feature was actually done.

3. What is one thing you would do differently?

I would resolve open design questions before implementation instead of during it. My issue left several questions open: which speed options to offer, whether failed uploads should be retried or removed, and how to display the speed. I ended up answering them while coding (2 to 10 second options, both Retry and Remove, and labels in seconds). It worked out, but discussing them with my team first would have made my estimate more accurate and given others a chance to weigh in. I would also spend more time on edge cases up front. For example, a user could delete the slideshow while images are still uploading, or an upload could finish after the editor closes. I caught these during implementation and added tests for them, but planning for them earlier would have saved rework.
