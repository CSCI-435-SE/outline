  How email settings work now

  All email configuration comes from environment variables. None of it is stored
  in the database:

  - server/env.ts:397-475 defines SMTP_HOST/SMTP_SERVICE (you can set only one
    of them), plus SMTP_PORT, SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM_EMAIL,
    SMTP_REPLY_EMAIL, SMTP_SECURE, SMTP_DISABLE_STARTTLS and SMTP_TLS_CIPHERS.
    It also works out EMAIL_ENABLED from them.
  - server/emails/mailer.tsx builds the nodemailer transport from env.*
    (getOptions() at line 288). The sender and reply-to addresses are set at
    line 185. In development, if SMTP_USERNAME isn't set, it uses a test
    account.

    env.EMAIL_ENABLED.
  - app/scenes/Settings/Authentication.tsx:283 is the only place in the UI that
    mentions email config. It disables the email sign-in toggle and shows "The
    server must have SMTP configured" when SMTP isn't set.

  1. Where are the SMTP environment variables defined and validated?
  - They're defined in server/env.ts:397-476 as fields on the Environment class.
  - The checks are decorators on those fields:
    - SMTP_HOST and SMTP_SERVICE can't be used together (@CannotUseWith,
      server/env.ts:399 and :406).
    - SMTP_SERVICE must be one of nodemailer's well-known services
      (@IsInCaseInsensitive, server/env.ts:407).
    - SMTP_PORT must be a number and can't be combined with SMTP_SERVICE
      (server/env.ts:423-425).
    - SMTP_FROM_EMAIL and SMTP_REPLY_EMAIL must be valid mailbox addresses
      (@IsMailboxAddress, server/env.ts:441 and :449).
    - SMTP_NAME, SMTP_USERNAME, SMTP_PASSWORD, SMTP_TLS_CIPHERS, SMTP_SECURE and
      SMTP_DISABLE_STARTTLS have no checks at all.
  - The checks run once, in the constructor on the next tick
    (server/env.ts:34-46). If any fail, the process exits with process.exit(1).
    Settings saved through the database would skip this, so you'll need to
    validate them separately.
  - EMAIL_ENABLED is worked out from these values at server/env.ts:410-412. It's
    marked @Public, so it's sent to the browser; the client reads it at
    app/scenes/Settings/Authentication.tsx:283.

  2. Where is email actually sent?
  - Mailer.sendMail calls transporter.sendMail at server/emails/mailer.tsx:183.
  - That is called from BaseEmail.send() at
    server/emails/templates/BaseEmail.tsx:164.
  - Several places read env values while sending, and each would need to check
    the database setting first:
    - server/emails/mailer.tsx:185: the reply-to falls back to
      env.SMTP_REPLY_EMAIL, then env.SMTP_FROM_EMAIL.
    - server/emails/templates/BaseEmail.tsx:207-216: the sender address comes
      from env.SMTP_FROM_EMAIL.
    - server/emails/mailer.tsx:266-288: the Mailgun, SES and Postmark detection
      reads env.SMTP_HOST and env.SMTP_SERVICE.

  3. Is the transport built once at startup or on each send?
  Once. It's built in the constructor at server/emails/mailer.tsx:58-61, and the
  module exports a single shared instance with export default new Mailer() at
  server/emails/mailer.tsx:347. sendMail just reuses this.transporter
  (server/emails/mailer.tsx:147). If an admin changes the settings, the
  transport won't pick them up until it's rebuilt or the process restarts.

  4. Is email sent from the API process or a queue worker?
  From the queue worker, though the decision to send is made in the API process.
  - BaseEmail.schedule() (server/emails/templates/BaseEmail.tsx:59-87) runs in
    the API process. It first checks env.SMTP_FROM_EMAIL and quietly does
    nothing if it's missing (line 61). Otherwise it adds an EmailTask job to the
    task queue, with 5 attempts and exponential backoff.
  - The worker picks the job up through taskQueue().process at
    server/services/worker.ts:163-164. EmailTask.perform then calls email.send()
    at server/queues/tasks/EmailTask.ts:20.
  - By default SERVICES is "collaboration,websockets,worker,web"
    (server/env.ts:353), so all of these run in one process. Deployments can
    split them into separate processes, and then each has its own Mailer. A
    setting change would need to reach the worker processes.
  - I found no .send() calls that bypass the queue outside tests.

  5. Is there an existing place that stores per-workspace settings as JSON?
  Yes, Team.preferences, a JSONB column.
  - The column is at server/models/Team.ts:236-237.
  - setPreference and getPreference are at server/models/Team.ts:313-337.
    getPreference falls back to defaults in shared/constants.ts:27.
  - The keys are the TeamPreference enum (shared/types.ts:430), and the value
    types are in TeamPreferences (shared/types.ts:464).
  - The API checks them with the schema at server/routes/api/teams/schema.ts:44,
    and teamUpdater saves them at server/commands/teamUpdater.ts:69.
  - Warning: the team presenter sends the whole preferences object to clients
    (server/presenters/team.ts:22). An SMTP password stored there would leak.
  - For encrypted columns, there's an @Encrypted decorator (AES-256 with
    SECRET_KEY) in server/models/decorators/Encrypted.ts. It's already used in
    server/models/IntegrationAuthentication.ts:47-58.

  6. Is there a model for server-wide settings, or only per-team data?
  I couldn't find one. No model in server/models/ stores settings for the whole
  installation, and no migration names suggest one. Everything I found is per
  team, per user or per integration. Since SMTP config applies to the whole
  server, you'll have to decide between a new table and storing it per team.
  "Admin" in this codebase means a team admin.

  7. How do models record who changed something and when?
  - When: every model gets createdAt and updatedAt from
    server/models/base/IdModel.ts:23-27. Team also gets deletedAt because it
    extends ParanoidModel (server/models/Team.ts:78).
  - Who: there's no general field for this. Some models add their own columns,
    such as Document.lastModifiedById and createdById
    (server/models/Document.ts:768 and :775). Team has nothing like that.
  - Otherwise, the record of who changed what lives in the event log (item 8).

  8. Is there an event log pattern?
  Yes.
  - The Event model (server/models/Event.ts) stores name, actorId (line 120),
    teamId (line 134), ip (line 53) and a changes JSONB column (line 73).
  - When a model is saved through saveWithCtx or updateWithCtx
    (server/models/base/Model.ts:61 and :79), an @AfterUpdate hook
    (server/models/base/Model.ts:225) calls insertEvent
    (server/models/base/Model.ts:256). It writes an event named like
    teams.update, with the actor and the before/after changes (changes: 
    model.previousChangeset, server/models/base/Model.ts:320). This only happens
    when the context has event.publish set.
  - Event.createFromContext (server/models/Event.ts:170) is the manual way to
    log an event.
  - After the transaction commits, each event is put on globalEventQueue
    (server/models/Event.ts:91-96).
  - Columns marked @SkipChangeset are left out of changes.
  - To check: Event.teamId is typed as a non-null string
    (server/models/Event.ts:134). I didn't check the migration to see whether
    the database actually requires it, which matters if the settings are
    server-wide rather than per team.

  What I didn't check
  - Whether any frontend code besides server/presenters/team.ts reads
    preferences in a way that would expose secrets.
  - Whether any tests mock mailer in a way that a rebuildable transport would
    break.

  server/migrations/20261119000000-create-email-settings.js (new)

  What: creates email_settings, with one row per setting. Columns are key
  (unique), value (JSONB), updatedById (references users, and becomes NULL if
  that user is deleted), createdAt and updatedAt. down drops the table. I ran it
  down and up on the test database and it worked.

  Why: one row per setting lets each value record who changed it and when. JSONB
  keeps the port as a number and the host as a string.

  What could go wrong:
  - These settings apply to the whole server; there's no teamId. If one
    installation hosts several teams, any team's admin would change email for
    every team. This is a design choice you should confirm.
  - down deletes every saved setting for good.
  - updatedById can be NULL in the database even though the model requires a
    user. That's deliberate: if a user is fully deleted, their settings stay and
    only lose the "changed by" link. As a result, the database alone doesn't
    guarantee a value is there.
  - The database doesn't generate id; the model does. Anything that inserts rows
    with raw SQL has to supply one.
  - There's no history. Each row only remembers the last person to change it and
    when. A full history would need the Event log, which has the non-null
    teamId problem I raised earlier.

  server/models/EmailSetting.ts (new)

  What: the model has two parts:
  - Checks on save:
    - Host can't be empty or just spaces.
    - Port must be an integer from 1 to 65535.
    - The from address must pass isMailboxAddress, the same check the
      SMTP_FROM_EMAIL env var uses.
    - Unknown keys are rejected.
    - Every save needs a user.
  - EmailSetting.resolve():
    - Returns { host, port, fromEmail }, each as { value, source: "admin" | 
      "environment" }.
    - A stored value that fails the checks is ignored, and a warning is logged
      with the key name only.

  Why: AGENTS.md puts business logic in models. The same function is used for
  both checks, so the rules for saving and reading can't drift apart. Env values
  are read on every call, so changes take effect without a restart.

  What could go wrong:
  - Mixed sources. Each setting is resolved on its own, so the admin's host can
    end up with the env's port, which may be meant for a different server.
    Per-value sources are what the design asks for, but the admin page should
    make this visible.
  - Conflict with SMTP_SERVICE. The env config refuses SMTP_HOST and
    SMTP_SERVICE together. If the env sets SMTP_SERVICE and an admin saves a
    host, resolve() returns the admin host while the service is still set.
    Nothing handles that yet.
  - Wiring it in. resolve() queries the database on every call. Once the mailer
    uses it, that's a query per email, and the transport is still built once at
    startup. Caching would bring back the stale-value bug the removal test
    caught. Each worker process also needs to rebuild its transport after a
    change.
  - Log noise. An invalid row logs a warning every time resolve() runs.
  - Env values aren't checked. The env vars have weaker checks; for example,
    SMTP_PORT=0 passes env.ts. Env values pass through resolve() unchanged, as
    you asked.
  - Loose types.
    - value is typed string | number for every key rather than per key, so
      callers have to narrow it.
    - updatedById is typed string | null, so TypeScript won't catch a missing
      user; only the runtime check will.
  - No permission check. Any user ID is accepted as "changed by". Checking that
    it's an admin belongs in the API policy, which you asked me not to touch.
